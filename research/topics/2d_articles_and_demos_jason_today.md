## jason.today (Jason McGhee)

Two interactive three.js articles with every demo's GLSL inline in the page: part 1 (https://jason.today/gi, 2024-07-27) builds naive 2D GI on a jump-flood distance field, and part 2 (https://jason.today/rc, 2024-08-31) builds RC on top of it step by step ([part 1](../sources/2024_mcghee_building_realtime_gi_part1.md), [part 2](../sources/2024_mcghee_building_realtime_gi_part2_rc.md)). Part 2 names Yaazarai's GM Shaders post as its biggest direct influence and thanks the paper's repository; part 1's introduction links the technique document on Google Drive. Part 2's interval formulas, tile layout, merge clamp, cascade count, Reduce Demand mode and derived interval table are in [cascade layout](cascade_layout_and_merging.md#intervals), its artifacts, limits and the article-against-code differences in [artifacts and fixes](artifacts_and_fixes.md#base-ray-counts-other-than-4), and its penumbra hypothesis and brute-force cost estimate in [core theory](core_theory.md#the-penumbra-hypothesis).

### Part 1: naive GI

**Drawable surface.** Strokes paint a float scene texture: rgb is the paint colour, alpha 1 where painted and 0 where empty. A GPU stroke pass copies the previous scene (`inputTexture`) and reads `color`, the segment endpoints `from` and `to` in pixels, `radiusSquared`, `resolution` (W, H) and the `drawing` flag; while drawing, it writes `vec4(color, 1)` where the squared distance to the stroke segment is at most `radiusSquared` (25 for the default 5 px radius). The segment distance projects the pixel onto the segment, clamps the parameter to `[0, 1]` and returns the squared remainder, avoiding a square root; both endpoint y values are flipped (`height − y`) because canvas y grows downward and UV y upward. Targets are RGBA `FloatType`, nearest, clamp to edge, two per pass as a ping-pong pair, cleared with `renderer.clearColor()` with no clear colour set.

**Naive raymarch.** Each empty pixel casts `N` rays at `TAU/N·(i + noise)` with `noise = rand(uv)`, directions `(cos, −sin)/size` so a step moves one pixel, and averages the colour of the first painted pixel each ray reaches, stopping at the canvas edge; painted pixels (alpha above 0.1) return their own colour and cannot receive light. The script differs from the article: noise is the constant 0.1 when the noise toggle (`showNoise`) is off; step `k` samples `uv + direction·k` from `initialStep` to `maxSteps − 1`, where `initialStep` is 0 with "accumulate radiance" on and `maxSteps − 1` with it off, so with it off each ray tests one texel and the rays show as separate dots; the hit test is alpha above 0.5 while the early return stays at 0.1; there is no sun or sky. The demo uses 8 rays and 128 steps by default (slider 0 to 512), both toggles on; the author says light spreads at most 256 px, the loop repeats overlapping work that neighbouring pixels cannot share (the motivation for the jump flood), the core loop is nearly the same as far more efficient methods, and the random offset avoids aligned rays and repeating patterns, with any cheap noise working and the goal being to use none.

**Jump flood.** The seed pass writes `vec4(uv·a, uv·(1 − a))`, so painted pixels hold their UV and empty ones `(0, 0)`; only rg is read later. `P = ceil(log2(max(W, H)))` passes (set in `innerInitialize`), 9 at 300×300 and 300×400, use offsets `2^(P−1−i)` px (256 down to 1, computed in `jfaPass` and passed as `uOffset` with `inputTexture`, `oneOverSize` and `skip`); each samples the 3×3 grid at `uv + (dx, dy)·o_i/(W, H)` including the centre, skips samples outside `[0, 1]²` and samples whose rg is `(0, 0)`, keeps the seed nearest to the current UV by squared distance, and writes rg with ba 0, or `(0, 0)` when nothing qualifies. There is no early exit, because "closer" depends on the stored seed, not on the jump length, and two targets ping-pong because a pass cannot read and write one target. The JFA demo's slider runs 0 to 9 passes (5 by default) with offsets still taken from `P`, so a partial run uses the largest offsets first; "No Passes" shows the UV map through a `skip` path. The distance pass writes `d = clamp(distance(uv, JFA.rg), 0, 1)` in UV units as `vec4(d, d, d, 1)`, and the DF demo always runs all `P` passes.

**GI with the field.** Each empty pixel casts 32 rays (`rayCount = 32.0`, a value only in the code) at `angle_i = stepAngle·(i + offset) + sunAngle`, with `offset = rand(uv + coef)` when noise (`showNoise`) is on and 0 when it is off (`coef` is the frame time with temporal accumulation, else 0) and `stepAngle = TAU/N`, to which an optional "sand grain" mode adds `offset·TAU`. Directions are unit vectors in UV, not divided by size. From `p = uv`, for steps 1 to `maxSteps − 1`, the march reads `d = DF(p)` with nearest sampling, moves `p += dir·d`, stops with no hit outside `[0, 1]²`, and on `d < EPS` (0.001) adds the scene colour at the moved `p`, marks a hit and stops, so the distance is read before the move and the colour after. Misses add `sunColor·smoothstep(1, 0, angleToSun) + skyColor` (in `sunAndSky`) when the sun is on, with `angleToSun = mod(angle − sunAngle, TAU)`, sun (0.95, 0.95, 0.9) and sky (0.02, 0.08, 0.2); the sky term is constant and the sun depends only on the ray angle, a model the author made up after finding others complicated or copied. Painted pixels are not marched: they emit their own colour if `length(rgb) ≥ 0.1` and are black occluders otherwise (only #000000 in the palette). Output `max(scene.rgb, radiance/N)` with alpha 1. With the field, max steps "can be way smaller" (32 against 256) and set quality and scale with canvas size; at the defaults a pixel reads the field at most 992 times plus one scene read per hit (derived).

**Temporal accumulation**, "basically a hack to deal with noise" that RC "does not need", adds the frame count to the noise seed (`rand(uv + time)`) and mixes `mix(new, previous, 0.9)` while `time < 10` (`accumAmt`); at the limit the next render resets time, skips the blend and stops the animation loop. It pauses while drawing (each stroke resets time), while a slider is pressed (`drawingExample`) and while toggled off; two ping-pong GI targets hold the history, and the screen renders a second time after the history pass (the sequence in `GI.renderPass`, derived from the code), at the cost of a target switch and an extra lookup per frame.

**Parameters.** Demo canvases 300×300 (simple, naive, JFA, DF) and 300×400 (GI, `new GI({ id: "gi", ... })`); stroke radius 5 px; naive 8 rays and 128 steps (the text says "like 256 steps"); painted threshold `alpha >= 0.1`; flood 9 passes, 3×3 with the centre; DF clamp 1.0 UV; GI 32 rays (the ray count and the DF clamp are in code only, not in the article text), max steps 32 (slider 0 to 48, loop runs `maxSteps − 1` times), `EPS` 0.001 UV; sun angle 4.2 rad (slider 0 to 6.2, step 0.1; the code comment says `TAU − 2.0`, about 4.28); accumulation 10 frames at 0.9 history; hash `fract(sin(dot(co, vec2(12.9898, 78.233)))·43758.5453)`.

**Article against code.** The article's seed is `vec4(vUv·alpha, 0, 1)` and the script's `vec4(vUv·alpha, vUv·(1 − alpha))`; the article initializes the flood with `vec4(−2.0)` and copies the full vector, the script with `vec4(0.0)` and copies `.xy`; the naive hit threshold is 0.1 in the article and 0.5 in the script; the article starts one step out while the script samples from step 0 (the empty pixel itself); the article always uses `rand(uv)`; the article mixes accumulation every frame while the script mixes only when `time > 0` and not drawing or sliding, and renders the GI pass twice. Read from the code: on the 300×400 canvas the GI rays and field are in UV units, so ray spacing and distances are not uniform in pixels (`oneOverSize` is declared and unused, while the naive shader divides by size); an unseeded pixel measures its distance to the UV corner, clamped to 1, and partial floods can leave pixels unseeded; no gamma or colour-space conversion appears anywhere.

**Stated limits and cost.** No timings, hardware or frame rates; the naive method is "wildly inefficient" and the canvas cannot grow much and stay smooth even on strong machines; part 2 promises the same result at much higher resolution and much better efficiency. Only painted surfaces are handled (reflective, transparent and subsurface materials need more), the sky is one colour and the sun one falloff, noise is needed against patterns and accumulation works around it. Ringing, leaks, aliasing, banding and flicker are not discussed. A Markdown gist of the post (`e78bc628…`) has the same demo constants but is an earlier text: the sentences about 8 rays reaching 256 px and "like 256 steps" appear only on the page.

### Part 2: building RC

**Motivation.** Part 1's stop test is an epsilon the author calls hand-wavy, and its quality came from 32 rays, style and accumulation. Raising the ray count mid-march is a branch the author calls not GPU friendly, and the distance field already skips steps, so lowering resolution with distance is not obvious; the answer is separate passes, a high-resolution one with few rays and a low-resolution one with many. Below, the article is the page's prose and snippets, the code is the scripts embedded in the page, and derived numbers come from the code's formulas at default settings. The page's canvases, in order (300×400 except the last):

|---|---|---|

| Penumbra, naive (`penumbra-hypothesis-canvas`) | PenumbraHypothesis, extending OnePassRaymarch | the same shader at 512 rays with noise and no sun |
| Two-pass (`two-pass-raymarch`) | TwoPassRaymarch, `two-pass-raymarch-fragment` | base pass with `baseRayCount` rays (default 16) at full resolution over `[0, partial]`; high-ray pass with `base²` (256) rays at `floor(coord/2)·2` over `[partial, √2]` (the article's first configuration is 256 rays at 1/16 resolution, then 16 at full resolution, and its host loop runs `i` from 2 down to 1 with `rayCount = base^i`, rendering `i > 1` into `lastTexture` by ping-pong and `i = 1` to the screen), so 3 of 4 rays are redundant; `partial` 0.125 (an arbitrary eighth of UV space) with no slider; the base pass merges misses by sampling the upper texture at the same UV and adding it linearized; `srgb` 2.2, output always encoded; base slider 4 or 16 |

| Penumbra with RC (`penumbra-hypothesis-canvas-rc`) | PenumbraHypothesisRC, extending MultipassRaymarch | the multipass shader at base 4 with no sun, `srgb` fixed at 1.0, linear filtering, no sliders, colours light, black and erase |
| Final (`radiance-cascades-canvas`) | RC, extending DistanceField, `rc-fragment` | everything below, 512×512 by default |

**Packing directions into pixels.** For base 16 the high-ray pass runs on a 4 px probe grid, one probe per 16 pixels: `spacing = 1` for the base pass and `√base` otherwise, `size = floor(resolution/spacing)` probes per axis, `probeRelativePosition = mod(coord, size)`, `rayPos = floor(coord/size)` picks the group of rays a texel holds, `baseIndex = baseRayCount·(rayPos.x + spacing·rayPos.y)`, ray `index = baseIndex + i` at angle `(index + 0.5)·TAU/rayCount`, probe centre `(probeRelativePosition + 0.5)·spacing`. Sixteen directions sit in 16 quadrants of a 4×4 grid, each quadrant one upper tile, numbered from the bottom left rightward and then up with a clockwise rotation. The merge decodes `upperPosition = (mod(index, √base), floor(index/√base))·upperSize` and samples at `(upperPosition + (probeRelativePosition + 0.5)/√base)/resolution`. Each output pixel then costs 2 × 16 = 32 raymarches, the same as the 32-ray naive method, while the penumbra hypothesis predicts better accuracy from 256 directions against 32. One sample per pixel group leaves a grid pattern, and linear filtering on the target gives bilinear upscaling "for nearly free".

**Tuning the split.** The ideal split is close to zero but not zero; about 0.02 UV (about 8 px) looks a little long but reasonable; the author's rule of thumb is half the probe width, 8 px for 16 px probes, probably too long. Shadows shift in proportion to the upper interval's offset and look reasonable with a lower split. With 16 px probes and 256 rays the upper interval would need about 128 px, which needs another layer, and that leads to the general form: `N_k = base^(k+1)` rays, spacing `√base^k`, start `base^(k−1)/shortestSide` (0 at cascade 0), length `base^k/shortestSide`, a lowest cascade covering 1 px from the probe centre, and `scale = shortestSide/resolution` per axis to keep rays on a unit circle on non-square canvases. The cascade count `ceil(log(diagonal)/log(base)) + 1` comes from 300×400: the longest ray is 500 px, `log4(500)` is about 4.5, so at least 5 cascades, and the `+1` was added when a top-left light did not reach the far edge ([layout](cascade_layout_and_merging.md#cascade-count)).

**sRGB and ringing.** Scene reads are linearized with gamma 2.2 and the output encoded with 1/2.2, since WebGL works in sRGB and light should add in linear space (the page links Shadertoy McSyWm); the author says this "produces a much brighter (accurate) result" and exposes vanilla RC's ringing, seen best with a single dot. The post calls the method still under active research and mentions 3D RC work by others without details. Ringing is "still an active area of research", with known fixes that "incur a fair amount of overhead (as in doubling the frame time) or cause other artifacts"; the penumbra appendix shows subtle ringing in the shadow. The final page carries a hidden "Ringing Fix" checkbox (`display: none`) read into `this.ringingFix` and never used.

**Final demo: sizes.** Query parameters `width` and `height` (512 on desktop, 300×400 on mobile), `pixelRatio` (2, `dp` in the code), `rcScale` (equal to it) and `autosize=true`, which scales the CSS size when the canvas is wider than the window minus 80 px. The simulation size (drawing, flood, field and RC targets) is `pixelRatio·width/rcScale`, unrounded, 512 at the defaults; the backing store is 1024, the CSS size 512, the high-resolution drawing and overlay targets 1024, the probe extent `floor(W_s/P)`. The RC targets are allocated at the simulation size, not the extent, so texels beyond the extent repeat. The brush radius is `4·pixelRatio` = 8 drawing px, divided by `rcScale` in the simulation pass. The RC reads the low-resolution scene and the overlay the high-resolution one.

**Final demo: pipeline.** Each frame draws the stroke into the simulation and high-resolution targets with a thin white cursor outline, seeds `(vUv·round(alpha), 0, 1)`, runs `ceil(log2(max(W_s, H_s)))` flood passes (9 at 512) over the 3×3 neighbourhood with out-of-range samples skipped, writes `clamp(|vUv − nearest|, 0, 1)` to red from `JFA(floor(vUv·resolution))`, renders the cascades from the top, and overlays. `angularSize = √(W_s² + H_s²)` = 724.08 gives `ceil(log4(724.08)) + 1` = 6 cascades with a literal base 4, so the Base Ray Count slider does not change the count; the Pixels Between Base Probes slider re-runs `initializeParameters(true)`, which resets the count uniform. The `animate()` loop keeps rendering about 1 s after the last mouse event. Uniforms: `cascadeInterval` 1.0, `rayInterval` 2.0, `intervalOverlap` 0.04, `baseRayCount` 4, `sunAngle` 4.2, `srgb` 1.0 or 2.2, `firstCascadeIndex` from Layer to Render; `lastCascadeIndex` is declared and never set or used, and `time` is set to 0.1 in JavaScript and not declared in the shader. Constants: `SQRT_2 = 1.41` (rounded), `PI = 3.14159265`, `sunDistance = 1.0`, sky `(0.2, 0.24, 0.35)·6`, sun `(0.95, 0.9, 0.8)·4`; the march stops after at most 100 iterations.

**Final demo: shader.** Its uniforms include `sceneTexture` (the low-resolution scene, rebound each pass), `distanceTexture` (the field, set each pass), `lastTexture` (the previous cascade, null for a frame's first pass in full mode), `cascadeExtent` (`(floor(W_s/P), floor(H_s/P))`, 512 × 512 by default) and `enableSun` (the Sun button, off). A texel's `coord = floor(uv·E)`, its probe centre is `(probe + 0.5)·P·s`, and a ray's direction is `(cos ang, −sin ang)`. Cascade 0 returns painted pixels unchanged. Each ray calls `raymarch(centerUV, d, scale, invR, offsetUV, L, minStep)`, declared as `raymarch(p, d, scale, invR, offset, L, minStep)`: it starts at `start·b^(k−1)/R` along its direction, returns 0 if that point is outside `[0, 1)²` and leaves the loop when a step takes it outside, steps by the field value scaled by `min(R)` in pixels, and hits when the field is at most half a texel; a hit texel with alpha below 0.99 returns black, otherwise its colour raised to `srgb`. The merge returns the ray unchanged on a hit or at the top, and otherwise adds one `textureLod` of the upper tile `idx` at `clamp((probe + 0.5)/√b, 1, upSize − 1)`, at mip `log2(P)` when `P > 1`; the targets use `LinearMipmapLinearFilter`, `LinearFilter` for magnification and generated mipmaps, though the article states linear filtering only for the V2 demo. With the sun on (`enableSun` and `k` the top cascade; `sunAndSky`, used when Naive GI Noise is off), every top-cascade ray takes `max(sun(angle), m.rgb)` with no hit test, where `sun = mix(sunColor·max(0, cos t)^4, skyColor, 0.3)` for `t = mod(angle − sunAngle, TAU)`; with Naive GI Noise on, the old `smoothstep(1, 0, t)` sun with part 1's colours applies instead. Noise is `rand(uv·(k + 1))`, up to one ray step. Output is `acc.rgb` above the displayed cascade and `pow(acc.rgb, 1/srgb)` at it, alpha kept. Paint: alpha 1 texels occlude and emit (linearized when `srgb` is 2.2); alpha 0.5 to 0.99 occlude with zero radiance; erased texels are not seeds and do not occlude. The overlay, at `rcScale` times the simulation size with linear filtering, shows the high-resolution paint where `highRes.a > 0` only when Layer to Render is 0, and the cascade output otherwise; the display plane draws the brush indicator on top.

**Final demo: precision and cost.** Targets default to half float: a `#full-precision` checkbox referenced in the code is missing from the page, so the half-float path is always taken, except flood targets above 1024 px on non-mobile. No timing is measured: every demo constructs `GPUTimer(renderer, true)`, which disables the timer extension, and no hardware is named. The page's ways to lower cost are 2 or more pixels between probes, `rcScale` above 1, `pixelRatio` 1 and Reduce Demand. Full mode casts `b·E²` rays per cascade, 1,048,576 at the defaults and about 6.3 M per frame over six cascades (derived). The article's claims, all unmeasured: 16 RC rays cost about as much as 16 naive rays and give no noise, the two-pass design costs 32 raymarches per pixel, the linear-filter upscale is nearly free, and some ringing fixes double frame time.

**Article against code.** Part 2's text and final code differ in ten places. The interval modifier is `base < 16 ? 1.0 : √base` in the article, `base < 16 ? P : √base` in the final code and `base < 16 ? 1 : 4` in the multipass demo. The merge clamp is `[0.5, upperSize − 0.5]` in the article, `[1, upperSize − 1]` in the code and absent in V2. Cascade 0 starts at 0 in the article and at `1·base^−1` (0.25 px at base 4) in the code. The article's snippet encodes the output when `cascadeIndex > firstCascadeIndex`, the code when `cascadeIndex ≤ firstCascadeIndex` (the display cascade), opposite conditions. The snippet sets alpha to 1, the final `rc-fragment` keeps `acc.a` and the multipass demo forces 1. The final code applies the sun to every top-cascade ray with no non-opaque test, the multipass demo only to non-opaque rays. The article loops from `cascadeCount − 1` and the multipass demo from `cascadeCount`, whose extra top pass is never merged because the merge condition is false for both. The final code counts cascades in log base 4 whatever the base ray count, the multipass demo in the chosen base, with the shorter side for the slider limit and the diagonal in `rcPass`. The penumbra text says the low-resolution pass starts at `partial` where the code runs the high-ray pass from it. The article does not describe Reduce Demand.
